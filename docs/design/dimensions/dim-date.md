# Design Specification — `dw.DimDate`

## 1. Objective

Design and implement the `dw.DimDate` dimension to provide a centralized calendar dimension for analytical reporting across the Enterprise Data Warehouse.

The dimension enables consistent time-based analysis and serves as the conformed date dimension for all fact tables.

---

## 2. Source

Unlike most dimensions, `dw.DimDate` is **not populated from the AdventureWorks OLTP database**.

It is generated programmatically by the ETL process using a configurable date range.

---

## 3. Grain

One row represents exactly one calendar day.

There is exactly one record for every date within the configured range.

---

## 4. Business Key

```text
FullDate
```

Example:

```text
2026-08-07
```

Although `FullDate` uniquely identifies the calendar day, it is not used as the warehouse key.

---

## 5. Surrogate Key

```text
DateKey
```

Representation:

```text
YYYYMMDD
```

Example:

```text
20260807
```

Advantages:

- Human readable
- Naturally sortable
- No lookup required for most ETL processes
- Widely adopted dimensional modeling practice

---

## 6. Columns

| Column | Data Type | Nullable | Purpose |
|---|---|:---:|---|
| `DateKey` | INT | No | Surrogate key (`YYYYMMDD`) |
| `FullDate` | DATE | No | Calendar date |
| `DayNumberOfWeek` | TINYINT | No | ISO weekday number |
| `DayNameOfWeek` | NVARCHAR(20) | No | Monday, Tuesday, ... |
| `DayNumberOfMonth` | TINYINT | No | Day within month |
| `DayNumberOfYear` | SMALLINT | No | Day within year |
| `WeekNumberOfYear` | TINYINT | No | ISO week |
| `MonthNumber` | TINYINT | No | Month number |
| `MonthName` | NVARCHAR(20) | No | January, February, ... |
| `QuarterNumber` | TINYINT | No | Quarter |
| `YearNumber` | SMALLINT | No | Calendar year |
| `IsWeekend` | BIT | No | Weekend indicator |

---

## 7. Generation Strategy

The ETL process generates one row per calendar day.

Example:

```text
StartDate

↓

Generate dates

↓

Populate attributes

↓

Insert into dw.DimDate
```

No source-system dependency exists.

---

## 8. Calendar Rules

Business rules:

- One row per day.
- No duplicated dates.
- Continuous calendar.
- ISO week numbering.
- Gregorian calendar.
- Weekend derived from weekday.

---

## 9. SCD Strategy

```text
Not Applicable
```

Dates never change.

No historical versions are required.

---

## 10. Keys and Constraints

### Primary Key

```text
PK_DimDate
(DateKey)
```

### Alternate Key

```text
UNIQUE(FullDate)
```

This guarantees that each calendar date appears only once.

---

## 11. Indexes

Initial indexes:

```text
PK_DimDate
→ DateKey

UQ_DimDate_FullDate
→ FullDate
```

Additional indexes are unnecessary due to the relatively small dimension size.

---

## 12. Business Rules

1. Every calendar day must exist exactly once.
2. Dates are immutable.
3. No gaps are allowed.
4. DateKey must always follow the `YYYYMMDD` convention.
5. The dimension is shared by every fact table.

---

## 13. ETL Objects

Planned objects:

```text
etl.LoadDimDate
```

Expected flow:

```text
Generate Calendar

↓

dw.DimDate
```

---

## 14. Validation Criteria

The implementation is considered valid when:

- no duplicate dates exist;
- DateKey matches the calendar date;
- every generated date is unique;
- weekend values are correctly calculated;
- month, quarter and year values are correct;
- the generated range is complete.

## 16. Design Decisions (ADR Summary)

| ID | Decision | Rationale |
|----|----------|-----------|
| ADR-001 | `DateKey` uses the `YYYYMMDD` format | Human-readable, naturally sortable, and avoids surrogate key lookups during ETL. |
| ADR-002 | `DimDate` is generated by the ETL process | A calendar dimension is deterministic and should not depend on OLTP data. |
| ADR-003 | One row represents one calendar day | Ensures a consistent grain across all fact tables. |
| ADR-004 | `FullDate` is enforced as unique | Prevents duplicate calendar dates. |
| ADR-005 | `DimDate` does not implement SCD | Calendar dates are immutable and never require historical versioning. |
| ADR-006 | `DimDate` is a conformed dimension | The same date dimension is shared by every fact table in the Enterprise Data Warehouse. |
