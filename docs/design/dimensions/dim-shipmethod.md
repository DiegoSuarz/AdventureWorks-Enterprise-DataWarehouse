# DimShipMethod Design Specification

## 1. Purpose

`dw.DimShipMethod` provides the analytical shipping-method context used by the
AdventureWorks Enterprise Data Warehouse.

The dimension describes the shipping company and its associated tariff
parameters while preserving historical changes to shipping rates through
Slowly Changing Dimension Type 2 behavior.

---

## 2. Source System

Primary source:

- `AdventureWorks2022.Purchasing.ShipMethod`

The source contains the shipping-method master data used by AdventureWorks.

Relevant source attributes:

| Source Column | Description |
|---|---|
| `ShipMethodID` | Primary identifier of the shipping method |
| `Name` | Shipping company name |
| `ShipBase` | Minimum shipping charge |
| `ShipRate` | Shipping charge per pound |
| `rowguid` | Technical replication identifier |
| `ModifiedDate` | Date and time the source row was last updated |

`rowguid` is technical source metadata and is not required in the analytical
dimension.

---

## 3. Grain

One row represents one analytical version of a shipping method identified by
`ShipMethodID`.

Because tariff attributes are historized, a single `ShipMethodID` may have
multiple rows over time, but only one version may be current.

---

## 4. Keys

### 4.1 Surrogate Key

`ShipMethodKey`

- Data type: `BIGINT`
- Generated by the data warehouse
- Implemented as an `IDENTITY`
- Used by fact tables instead of the OLTP business key

### 4.2 Business Key

`ShipMethodID`

- Data type: `INT`
- Source: `Purchasing.ShipMethod.ShipMethodID`
- Stable identifier of the shipping method
- Classified as SCD Type 0

---

## 5. Target Attributes

| Target Column | Data Type | Nullable | Purpose |
|---|---|---:|---|
| `ShipMethodKey` | `BIGINT IDENTITY` | No | Data warehouse surrogate key |
| `ShipMethodID` | `INT` | No | Source business key |
| `ShipMethodName` | `NVARCHAR(50)` | No | Shipping company name |
| `ShipBase` | `DECIMAL(19,4)` | No | Minimum shipping charge |
| `ShipRate` | `DECIMAL(19,4)` | No | Shipping charge per pound |
| `EffectiveStartDateTime` | `DATETIME2(7)` | No | Start of analytical version |
| `EffectiveEndDateTime` | `DATETIME2(7)` | No | End of analytical version |
| `IsCurrent` | `BIT` | No | Indicates the active version |
| `RowHash` | `VARBINARY(32)` | No | Detects Type 2 changes |
| `SourceModifiedDate` | `DATETIME2(0)` | No | Last source modification timestamp |
| `CreatedAt` | `DATETIME2(7)` | No | Data warehouse creation timestamp |

---

## 6. Data Type Decisions

The source defines `ShipBase` and `ShipRate` using SQL Server `MONEY`.

The data warehouse stores both attributes as:

`DECIMAL(19,4)`

This preserves the source precision and scale while using an explicit,
portable numeric definition instead of the SQL Server-specific `MONEY` type.

The source `Name` attribute uses an AdventureWorks alias data type whose
physical base type is equivalent to:

`NVARCHAR(50)`

The data warehouse uses `NVARCHAR(50)` directly and does not replicate the
source alias type.

---

## 7. Slowly Changing Dimension Strategy

### 7.1 Type 0

`ShipMethodID`

The business key identifies the shipping method and must not change within an
existing analytical version.

### 7.2 Type 1

`ShipMethodName`

A shipping-company name change is treated as a descriptive correction or
update and does not independently require a new historical version.

### 7.3 Type 2

The following attributes represent tariff conditions and require historical
preservation:

- `ShipBase`
- `ShipRate`

A change to either attribute expires the current dimension version and inserts
a new current version.

---

## 8. RowHash

`RowHash` is calculated using SHA-256 and contains only the attributes that
participate in SCD Type 2 change detection:

- `ShipBase`
- `ShipRate`

The following attributes are deliberately excluded:

- `ShipMethodID`
- `ShipMethodName`
- `SourceModifiedDate`

This ensures that only tariff changes trigger creation of a new historical
version.

---

## 9. Temporal Model

Dimension versions follow a half-open temporal interval:

`[EffectiveStartDateTime, EffectiveEndDateTime)`

The start timestamp is inclusive and the end timestamp is exclusive.

When a Type 2 change occurs:

1. The current version is expired.
2. Its `EffectiveEndDateTime` is set to the transition timestamp.
3. `IsCurrent` is set to `0`.
4. A new version begins at exactly the same transition timestamp.
5. The new version is marked with `IsCurrent = 1`.

This prevents gaps and overlaps between consecutive versions.

---

## 10. Current-Version Constraint

At most one current row may exist for each `ShipMethodID`.

This rule will be enforced with a filtered unique index on the business key
where:

`IsCurrent = 1`

---

## 11. SourceModifiedDate

Because `DimShipMethod` uses a single source table:

`Purchasing.ShipMethod.ModifiedDate`

maps directly to:

`SourceModifiedDate`

No multi-table maximum timestamp calculation is required.

---

## 12. Source Profiling Findings

Source profiling identified:

- 5 total shipping methods
- 5 distinct `ShipMethodID` values
- 5 distinct shipping-method names
- no duplicate business keys
- no duplicate names
- no NULL values in relevant attributes
- no negative `ShipBase` values
- no negative `ShipRate` values

Observed tariff ranges:

- `ShipBase`: 3.9500 to 29.9500
- `ShipRate`: 0.9900 to 2.9900

`Sales.SalesOrderHeader` contains 31,465 sales orders.

All sales orders contain a valid `ShipMethodID`, with:

- 0 NULL shipping-method references
- 0 orphan shipping-method references

Only two shipping methods are currently used by sales orders:

- `XRQ - TRUCK GROUND`: 27,659 orders
- `CARGO TRANSPORT 5`: 3,806 orders

The remaining shipping methods remain part of the source master catalog and
must still be loaded into the dimension.

---

## 13. Analytical Interpretation

`ShipBase` and `ShipRate` are numerical attributes, but they are not
transactional fact measures.

They describe the tariff configuration of a shipping method:

- `ShipBase` = minimum shipping charge
- `ShipRate` = shipping charge per pound

Transactional shipping amounts belong to individual business events, such as
`Sales.SalesOrderHeader.Freight`.

Therefore:

- tariff configuration belongs in `DimShipMethod`
- transactional freight amounts belong in the sales fact process

---

## 14. Historical Limitation

The source system exposes the current state of `Purchasing.ShipMethod`.

The data warehouse can preserve tariff changes detected from the moment the
ETL process begins operating, but it cannot reconstruct tariff versions that
were overwritten in the source before the data warehouse captured them.

---

## 15. Load Flow

The expected data flow is:

`Purchasing.ShipMethod`
→ `stg.ShipMethod`
→ `dw.DimShipMethod`

The staging layer will provide a normalized current-state representation of
the source and calculate the Type 2 hash required by the dimension-loading
procedure.
